# PERF-51 — completato il 29 settembre 2026

## Esito

Dashboard v1 ridotta da tre query aggregate a una query MySQL tradotta server-side. La propagazione della cancellazione,
il cleanup async e l'invariante del saldo concorrente sono verificati. Nessun indice o migration è stato aggiunto.

## Modifiche

- Propagato il CancellationToken dai controller legacy/v1 a servizi, comandi, query EF, policy di ownership/coppie e
  preflight. Anche l'endpoint profilo passa RequestAborted all'accesso EF diretto.
- Rollback usa CancellationToken.None per completare la pulizia anche dopo l'abort. Transazioni e context temporanei
  di retry vengono smaltiti con DisposeAsync.
- Convertite in API EF asincrone le verifiche sync residue nei percorsi di comando.
- La dashboard aggrega redditi, spese e categorie in una GROUP BY, mantenendo i totali e il criterio storico con cui
  una categoria netta viene assegnata a entrate o uscite. Il singolo statement offre anche una vista coerente dei dati.
- Il lock wallet usa il risultato corrente di SELECT FOR UPDATE per aggiornare l'entità già tracciata, così retry e
  mutazioni serializzate non salvano una BalanceVersion obsoleta.
- Lo snapshot OpenAPI legacy è stato rigenerato: ora include la route /metrics già esposta da OBS-50.
- Il test host MySQL effimero ora fornisce una configurazione di logging valida richiesta da OBS-50.

## Misurazione dashboard

MySQL 8.4 effimero Testcontainers; 1.000 movimenti sintetici (600 entrate e 400 uscite), filtro mensile fisso,
8 warm-up e 50 richieste seriali. Allocazioni stimate con il contatore process-wide prima/dopo il campione e divise
per 50; sono approssimative e dipendono dal runner.

| Misura | Prima | Dopo |
|---|---:|---:|
| Query per richiesta | 3 | 1 |
| p50 | 5,577 ms | 2,824 ms |
| p95 | 6,429 ms | 3,466 ms |
| Allocazioni approssimative | 124.855 B/richiesta | 74.745 B/richiesta |

Il SQL MySQL eseguito usa un'unica GROUP BY su tipo e due SUM(CASE WHEN Value > 0 / Value < 0) più la somma netta per
categoria. La sonda d'integrazione stampa il SQL effettivo e verifica totali/categorie attesi. Riduzioni osservate:
66,7% round-trip, 49,4% p50, 46,1% p95, 40,1% allocazioni approssimative.

## Limiti documentati

Le API UserManager/SignInManager di ASP.NET Identity non espongono overload con CancellationToken. Le chiamate account
che le usano rimangono awaited e non vengono staccate in background; gli accessi EF diretti ricevono il token HTTP.
La misura è una baseline riproducibile sintetica, non un SLO di produzione né un test di latenza su un volume reale.

Non sono stati cambiati contratto DTO, logica monetaria o schema DB.
