# Evidenza completamento Fase 0 — 21 settembre 2026

## Esito

La Fase 0 è completata. La suite backend non contiene più credenziali o destinazioni MySQL hard-coded, crea un
container MySQL 8.4 posseduto dal singolo run, caratterizza il contratto HTTP legacy e non include più la dipendenza
Playwright vulnerabile e inutilizzata.

## TST-01 — MySQL effimero e guardie

- `Testcontainers.MySql 4.15.0` avvia `mysql:8.4` una volta per assembly.
- Ogni run genera run-id, database `mg_test_<run-id>`, utente, password e porta casuali.
- `MoneyGestorContext` riceve la configurazione dal fixture; `DatabaseFactory.InTest` e i valori
  `localhost:1883` / `ut_money_gestor` / `psw_ut` sono stati rimossi.
- Nessun test invoca più `EnsureDeleted`; il database scompare con il container posseduto dal fixture.
- La guardia richiede contemporaneamente modalità test, run-id, prefisso/nome database, host, porta e container-id.
- Sei casi negativi verificano il rifiuto prima del cleanup quando una guardia non coincide.
- Run osservati con ID/database differenti, fra cui `015b0166…` e `aa844a02…`.
- Un run con ID `33d9b606…` è stato interrotto dopo l'avvio; `docker ps -a` non ha trovato il container etichettato
  dopo l'annullamento, confermando il cleanup del resource reaper.
- Senza Docker il fixture fallisce durante l'accesso al daemon, prima di inizializzare qualsiasi destinazione database;
  non esiste fallback automatico.

Comando ordinario:

```powershell
dotnet test backend/TestProject/TestProject.csproj
```

Prerequisito: Docker Desktop o un daemon Docker compatibile raggiungibile dal processo test.

## TST-02 — riparazione e caratterizzazione

Correzioni ai test legacy:

- `CorrectInsert_NegativeValue` esegue e verifica ora il command negativo corretto;
- le verifiche saldo recuperano il wallet tramite wallet-id, non correlando ID di entità diverse;
- `DeleteWhenTransactionNotEmpty_Throws` è un caso completo e verifica `NotValidForDeleteException`;
- le asserzioni sui tipi distinguono i due record globali dai record personali;
- `UserBase` e `UserManager`, percorso di setup legacy senza consumer produttivi, sono stati rimossi;
- non resta alcuna chiamata `Assert.Inconclusive`.

Nuova copertura:

- 7 casi sulle guardie di ownership del database;
- 5 characterization test HTTP con `WebApplicationFactory`: registrazione/login, envelope e casing JSON, errore login,
  validazione wallet, CORS corrente e documento Swagger;
- host `Testing` avviabile senza leggere settings o inizializzare un database esterno;
- 4 test cross-user `Explicit` che descrivono il comportamento sicuro atteso per wallet, colori, tipi e owner dei
  movimenti.

Il run ordinario comprende 73 casi: è passato tre volte consecutive durante l'implementazione e una quarta volta dopo
la rebuild conclusiva. I quattro casi `KnownSecurityGap`, eseguiti separatamente tramite filtro, falliscono tutti come
previsto e confermano i gap assegnati a SEC-11/SEC-12; non sono asserzioni verdi sul comportamento insicuro.
